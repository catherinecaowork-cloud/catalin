## Purpose

把「怎么登录被测站点」做成可插拔能力，并让登录结果同时服务接口回归与 UI 回放，避免同一个站点维护两套登录。这是「只要能登录就能测」这句话唯一能落地的地方。

## ADDED Requirements

### Requirement: 三种登录方式

平台 SHALL 支持 Cookie 注入、Token / 自定义 Header、表单登录三种登录器，并 SHALL 允许按站点选择其中一种。

#### Scenario: Cookie 注入登录

- **WHEN** 站点配置为 Cookie 登录且凭证有效
- **THEN** 执行器在浏览器上下文与接口客户端中都带上该 Cookie，访问需要登录的页面不再被重定向到登录页

#### Scenario: 表单登录

- **WHEN** 站点配置为表单登录并提供账号密码与登录页字段定位
- **THEN** 执行器在真浏览器中完成登录，并导出登录态供后续步骤复用

#### Scenario: 登录失败快速失败

- **WHEN** 凭证失效或登录页结构变化导致登录未成功
- **THEN** 运行以明确的「登录失败」原因结束，不继续执行后续业务步骤

### Requirement: 登录态在接口与 UI 之间共享

一次登录的结果 SHALL 可同时用于 L1 接口重放与 L2 浏览器回放，同一次运行内 SHALL NOT 要求重复登录。

#### Scenario: UI 登录结果供接口使用

- **WHEN** 一次运行先通过表单登录取得会话，随后执行接口请求集
- **THEN** 接口请求自动携带该会话凭证并被服务端认作已登录

### Requirement: 未支持登录方式的显式拒绝

对滑块验证码、短信 / 邮箱二次验证、企业 SSO 跳转等本期不支持的方式，平台 SHALL 在配置或运行时给出明确的不支持提示，而 SHALL NOT 以普通失败或超时形式表现。

#### Scenario: 遇到不支持的登录挑战

- **WHEN** 登录过程中出现验证码或二次验证挑战
- **THEN** 运行以「登录方式不支持，需扩展登录器」结束，并在结果中标明检测到的挑战类型
