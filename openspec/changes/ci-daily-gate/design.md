## Context

见 `proposal.md`。证据：

| 位置 | 事实 |
| --- | --- |
| `scripts/run_flow.py:15-43` | 入队后打印 run_id 即 `return 0`，不等待、不可能失败 |
| `scripts/run_flow.py:1` | docstring 自称「CI 里也用这个入口」 |
| `.gitee-ci.yml:6-12` | 只有一个 `pytest` 作业，测的是平台自身代码 |
| `api/flows.py:165` | `list_flows` 不带 status 过滤参数，闸门需自行按 `FlowOut.status` 筛选 |
| `models.py:93-104` | `Run.status` 取值 `queued / leased / running / passed / failed / error`；`finished_at` 标记结束 |
| `hub.py:41` | `notify_new_job` 是 Worker 长轮询的唤醒信号，**不是**告警通道 |

仓库里没有任何通知机制（无 webhook / 邮件 / 企微）。

## Goals / Non-Goals

**Goals:**

- 一条命令跑完 `active` 流程，失败时流水线变红
- 结果能定位到具体是哪条流程、哪次运行
- 空集与超时都不产生假绿

**Non-Goals:**

- 并行调度（串行跑，够用；内网 Worker 数量有限）
- 报告门户、趋势看板、历史对比
- 推送通知（钉钉 / 企微 webhook）——见 Decisions 第 2 条
- 按套件或标签分组跑
- 改控制面的任何接口

## Decisions

1. **新增闸门脚本，不动 `run_flow.py`**  
   `run_flow.py` 是「手动触发一条、看直播地址」的工具，保留其现有语义。闸门是另一个脚本，两者复用同一个控制面 API。  
   备选：给 `run_flow.py` 加 `--wait` 开关。否决——两种用途的默认行为相反（一个要立刻返回给人看地址，一个要阻塞到出结论），混在一个入口里迟早误用。

2. **退出码是唯一门禁信号，最小版不做推送**  
   Gitee 流水线页面本身就是通知渠道；在没有确认过内网可达的通知通道之前，加一个发不出去的 webhook 只是假动作。  
   备选：现在就接钉钉 / 企微 webhook。推迟——需要先确认内网出口与目标群，属于另一个决定。

3. **空集算失败，不算通过**  
   若有人误把所有流程退回草稿，闸门应当报红而不是报绿。假绿比红灯更有害：它让人以为回归在跑。  
   备选：空集时输出提示并返回 0。否决——见上。

4. **必须有总时限**  
   没有总时限时，一条卡住的运行会让流水线挂到平台自身的超时，那时既没有结论也没有线索。总时限到点即判失败并指出卡住的流程。

5. **闸门与触发器解耦**  
   脚本只依赖控制面 API 和退出码，不依赖 Gitee 的定时能力。这样即使 Gitee 不支持定时触发，也能用外部计划任务调用同一个脚本，行为完全一致。

## Risks / Trade-offs

- [前置依赖：`locator-popup-fix` 未落地时闸门天天红] → 明确把本 change 排在它之后。若要先上闸门，回归集合会长期非绿，红灯失去意义。
- [串行跑使一次回归耗时叠加] → 接受。`active` 流程数量在团队内网规模下可控；并行是后续能力。
- [闸门依赖控制面在线且有可用 Worker] → 启动前先确认有 Worker 可用；不可用时明确报错，而不是入队后卡在 `queued` 直到总时限。
- [按 `FlowOut.status` 客户端筛选，而列表接口不分页] → 当前流程数量小，可接受；若将来流程数增长，再加服务端过滤。

## Migration Plan

无数据迁移。回滚：从 `.gitee-ci.yml` 移除闸门阶段，脚本可留可删；不影响控制面与执行器。

## Open Questions

- 定时频率？（建议每天一次，在业务低峰；具体时点由使用者定）
- Gitee 流水线是否支持定时触发？若不支持，用外部计划任务调用同一脚本。
- 通知渠道若要加，走钉钉还是企微？（本 change 不做，留待确认内网可达性）
