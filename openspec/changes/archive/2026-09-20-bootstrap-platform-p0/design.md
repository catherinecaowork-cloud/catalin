## Context

动机见 [proposal.md](proposal.md) 的 Why；行为要求见 `specs/` 各能力规格。本文只讲怎么实现。

约束来自三处既有事实：

1. **被测系统多在内网**，值班电脑常在 NAT 后，CI Runner 临时起落——平台无法主动连接执行侧。
2. **现有资产可复用但绑着业务语义**：`api-test/webui` 已实现「拉子进程 + 泵 stdout + SSE 直播 + 心跳重连」；`shared` 有配置覆盖层、HTTP 封装、HAR 录制；`mes_agent` 有一段已证明有效的 JS 错误探针。但登录、版本、主数据、菜单中文名全是 MES 专用。
3. **两套浏览器驱动栈并存**：现仓库 `.venv` 用 Playwright，`.venv-bu` 用 browser-use 0.13.7 走 CDP（该环境里根本没有 playwright 包），两者依赖树与 `python-dotenv` 版本都冲突。

## Goals / Non-Goals

**Goals:**

- 一套动作原语同时服务回放与（P1 的）探索，使探索产物天生可回放
- 执行侧零入站端口即可工作
- 凭证不落明文，产物默认脱敏
- 控制面与执行器强类型共享 job / event 结构，减少联调摩擦
- 单机可部署，Worker 双分发（Windows 开窗 / 容器无头）

**Non-Goals:**

- 不做高可用与水平扩展（单机 Compose，接受无 HA）
- 不做实时视频流的低延迟优化，P0 用逐步截图满足可见性
- 不做流程可视化编辑器（P1 上前端框架后再做）
- 不写任何模型调用代码

## Decisions

### D1：浏览器驱动只用 Playwright，锁 1.49.1，不引入 browser-use

**为什么**：AI 探索的产物必须能被回放引擎执行。若探索用 CDP 动作、回放用 Playwright 定位，中间的「编译」环节要跨两套语义翻译，等于把最脆的环节做得最脆。统一之后，探索输出即回放步骤，编译只需补断言与固化定位。

**备选**：保留 browser-use 做探索（现成的 Agent 循环、DOM 序列化）。放弃原因是两套驱动栈、依赖树膨胀、以及翻译层的长期维护成本；P1 自研薄循环约 300–500 行可覆盖所需能力，且实测表明我们的定位不依赖模型看 DOM，序列化可以压得更狠。

**版本**：锁 1.49.1 与现 `ui-test` 一致（驱动已验证），不跟 `api-test` 的 1.59.0。Chromium 随 lock 固定，避免驱动漂移伪装成用例失败。

### D2：任务分派用「Worker 长轮询拉活」

**为什么**：平台只需一个可达入口，Worker 单向出网即可，内网与 NAT 后的机器都能接入。

**实现**：Postgres 任务表 + `FOR UPDATE SKIP LOCKED` 保证一个任务只被一个 Worker 领走；领取带租约与超时回收，Worker 崩溃后任务可被重新领取。

**备选**：Redis / RabbitMQ（P0 规模用不上，先不引）；平台主动推送（被防火墙否决）。

### D3：Worker 不碰数据库，job 自包含

**为什么**：Worker 要能扔进内网、CI、值班机，给它数据库连接等于把凭证与租户边界一起外扩。

**实现**：job JSON 携带站点、执行目标、可见性与产物选项；凭证以引用形式下发，Worker 用受控接口换取，仅在内存解密。`packages/protocol` 用 pydantic 定义 job / event / 步骤 DSL，控制面与 Worker 共享同一份模型。

### D4：探针用「上下文级初始化脚本」注入，而非进入应用后注入一次

**为什么**：现方案在进入应用后注入一次，依赖 SPA 不整页刷新这一假设。改为浏览器上下文的初始化脚本后，对所有页面与后续导航自动生效，整页刷新也不失效。

**通用化**：`fetch` 失败判定从硬编码 `/pamirs/` 改为站点可配置的 URL 模式，默认「任意 JSON 响应含非空 `errors`」；UI 框架相关规则（错误提示组件、加载指示器、表格结构、空态文案）下沉到 `packages/adapters`，核心探针不含框架类名。

**价值依据**：现网就靠这段探针抓到「某页面视觉完全正常、但某接口返回 HTML 错误页」——接口测试测的不是这个接口，人工点页面也看不出来。

### D5：定位用候选集打分，不产出单一选择器

**为什么**：单一选择器要么脆、要么被迫用哈希 class。候选集让回放有退路，也让「即将失效」可被观测。

**优先级**：稳定属性（`data-testid` 等）→ ARIA role + 可访问名 → label / placeholder 关联 → 适配器提供的框架锚点 → 结构化 CSS（低分）。命中低分候选记 `locator_drift` 预警——用例还没坏，但已经在坏的路上，这个信号比等它彻底失败有用。哈希 class 一律不采纳。

### D6：可见性是开关，不是第二套执行路径

**为什么**：如果无头是「只发接口、假装点过」，那 CI 结论就不可信。

**实现**：开窗与无头共用同一份步骤与同一套断言，只切 `headless`。远程跟看用逐步截图推流；容器无桌面会话，请求开窗时明确失败而不静默降级。

### D7：进度靠结构化事件，不靠正则解析日志

**为什么**：现方案用正则从日志文本里猜请求成败，还依赖特定后端的响应形状。平台化后这条路会随每个新站点而破。

**实现**：Worker 直接上报结构化事件（运行 / 步骤 / 请求 / 探针 / 断言）；控制面沿用现有 SSE 骨架（首包全量快照 + 增量 + 心跳 + 断线重连 + 结束补拉）。站点专用的响应判定放在适配器里注册，不进核心。

### D8：不把 pytest 当平台执行内核

**为什么**：平台要按步骤上报进度、按流程状态机调度、跨租户隔离，这些用 pytest 表达都要绕。

**取舍**：pytest 保留为「工程师自己写代码级用例」的并行入口。Allure 只做可选导出——它需要 JRE 与独立 CLI，镜像重且与平台数据模型两套。

### D9：意图确认落成数据库状态机

**为什么**：绿勾只能证明「脚本又跑通了」，不能证明「测的是我要的东西」。

**实现**：流程状态 `draft → reviewed → golden → active`，执行成功不自动推进；`golden` 要求一次被采纳的运行并固化基线；CI 门禁只跑 `active`。失败产生待审记录，分类由人终审。

### D10：内网单机 Docker Compose，控制面 P0 允许有状态

**为什么**：单机部署下 SSE 订阅者与事件缓冲放进程内存最简单，无需引入 Redis 做跨实例广播。

**留后路**：用户会话走 JWT、Worker 令牌落库，都不放内存。将来要多副本时，改的只是事件广播一处，不用重做认证。

**Worker 分发**：Windows 用 pip + CLI（开窗必须落在真实桌面），CI 用容器镜像（无头）；两者共用 `packages/executor`，差别仅在浏览器安装方式与 `headless` 默认值。

## Risks / Trade-offs

- **自研 Agent 循环的工作量**（P1）→ P0 完全不碰模型，先把动作原语与回放稳住；循环只是「观察→决策→执行→记步」，工具集复用回放引擎，不重复造定位能力。
- **没有稳定属性的站点定位质量差** → 候选集打分 + 允许人工钉定位 + 适配器插件；P0 验证站点故意选一个完全没有 `data-testid` 的，尽早暴露真实难度。
- **Flaky 让门禁不可信** → 自动等待优先于固定睡眠；定位漂移预警提前暴露；失败分类需人终审，避免把抖动当缺陷、也避免把缺陷当抖动。
- **共享测试环境被写脏** → 流程默认可标记 dry-run；写操作类流程需显式开启；建议 P0 验证站点使用独立账号。
- **单机无高可用** → 自觉接受；备份口径为 Postgres 逻辑备份 + 对象存储目录备份。
- **凭证泄露** → 控制面加密存储、Worker 内存解密、事件与 HAR 脱敏；凭证不可读回，只能覆盖。
- **Playwright 版本漂移伪装成用例失败** → 锁定版本并写入 lock，Worker 镜像与 pip 分发均固定同一 Chromium。
- **公司 LLM 网关协议未知**（P1 才阻塞）→ 若非 OpenAI 兼容，加一层薄适配；现在先把密钥模型按「按租户存 credential」设计，避免返工。

## Migration Plan

新建仓库，无存量数据迁移。

1. `autotest-platform` 独立成库，不放在 `mes-test-platform/packages/` 下——否则共享 MES 仓库的 CI、忽略规则与提交历史，将来独立发版还要再拆一次。
2. 现 MES 仓库保持原样继续运行，作为 `packages/adapters/oinone` 的素材来源与第一个内部客户。
3. 复用现有代码时逐个改造，不整体搬迁：直播骨架、配置覆盖层、日志、HAR 摘要、JS 执行层、探针错误劫持部分。
4. 明文敏感信息（内网地址、账号、数据库连接串、通知 webhook）不带入新仓库，一律进 credential 表。
5. 回滚策略：P0 阶段平台不承担生产职责，出问题直接停用 Compose，MES 原有测试链路不受影响。

## Open Questions

- P0 的两个验证站点具体选谁（需一个有稳定属性、一个完全没有）。不影响架构与任务拆分，只影响验收执行顺序。
- 公司统一网关是否为 OpenAI 兼容协议。P1 才用到；若不兼容，仅需在探索层加薄适配，不改本文决策。
